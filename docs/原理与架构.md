# 原理与架构

本文面向想读懂 VocalSeparator 内部实现的开发者，说明**它到底怎么把一首歌拆成人声和伴奏**、进度条为什么可信、集成（ensemble）是怎么融合的、以及离线与并发是怎么保证的。

所有结论都能在代码里找到对应位置，文中给出 `文件:行号`。凡是无法从代码确认的，会显式标注「待确认」。

### 两段式的特例：开启「人声去回声」时

开启去回声后，进度区间**不是** 0.06→0.94 一整段，而是被切成两段（`app.py:471`、`app.py:1298`）：

```python
P_DRE_LO = 0.56   # 分离（1/2）跑到 0.56，去回声（2/2）占 0.56 -> 0.94
sep_hi = P_DRE_LO if want_dre else P_SEP_MAX     # app.py:1298
```

也就是说「1/2 分离」和「2/2 人声去回声」各自在页面上占一段进度，用户能看出当前处在哪一阶段。

## 二、推理核心：STFT 分块与 RoFormer

### 2.1 参数从哪来

分离器由 `make_separator()`（`app.py:908`）构造，把 UI 参数翻译成 `audio-separator` 的 `mdxc_params`（`app.py:890`）：

```python
def _mdxc_params(seg, batch, overlap):
    ...
    "overlap": max(1, int(overlap)),
```

| 参数 | UI 默认 | 作用 | 代码位置 |
| --- | --- | --- | --- |
| `overlap` | **4** | 分块重叠倍率。越大，块与块的衔接越平滑，但计算量近似成正比 | `app.py:4871` / `app.py:4978` |
| `batch_size` | 8 | 一次送进 GPU 的块数，换显存为速度 | `app.py:4869` |
| `segment_size` | 0（跟随模型原生） | RoFormer 分段长度；0 表示用模型自带值 | `app.py:4870` |
| `demucs shifts` | 4 | 仅多轨 Demucs 模型，越高越精细 | `app.py:4872` |
| `demucs overlap` | 0.25 | 仅多轨 Demucs 模型 | `app.py:4873` |

> ✅ **官方默认值：`overlap = 4`（已裁决，以此为准）**
> 依据三处互相印证：
> 1. `app.py:4871` 与 `app.py:4978` 的 `gr.Slider(2, 64, value=4, ...)`；
> 2. 滑杆标签 `OVERLAP_LABEL`（`app.py:4822`）自己写着「重叠倍率 overlap（**4 默认·与 Roformer 训练配置一致** / 8 更保守 / 16 精细，越高越慢成正比）」——这解释了为什么选 4：**4 与 Roformer 自身的训练配置一致**，改动它等于让推理条件偏离模型训练分布；
> 3. `SECONDS_PER_AUDIO_SECOND = 0.30`（`app.py:472`）的注释自述是在「overlap=4 + native fp16、单模型」条件下测得的经验值。
>
> `app.py:18` 的「overlap 默认值 32 -> 8」与旧 `README.md:39` 的「默认 32」都是**过时的历史改造说明**，不是运行事实，请勿据此判断。
> 调参口径：**4 为官方默认**，**8 是更保守的可选值**（衔接更平滑、更慢），**16 精细**，越高耗时近似成正比。

### 2.2 为什么 overlap 是最大的速度变量

`overlap` 是「重叠窗口倍数」。越大，同一段音频会被**重复推理更多的份数**（`app.py:893-894` 的注释：`overlap=32` 相当于把同一段音频重复推理 32 倍）。

项目的「环境」页内置了一个**本机实测**按钮（`bench_perf_ui()`，`app.py:2481`），它用同一段 60 秒音频、同一模型跑 6 组配置（`app.py:2497-2504`）：

```python
configs = [
    ("当前设置",            int(cpu_threads or 0), bool(cudnn_benchmark),  8,  8),
    ("CPU 线程 = 4",        4,                     bool(cudnn_benchmark),  8,  8),
    (f"CPU 线程 = {n_cpu//2}（半数核心）", ...,                           8,  8),
    ("关闭 cudnn.benchmark", int(cpu_threads or 0), False,                 8,  8),
    ("batch_size = 16",     int(cpu_threads or 0), bool(cudnn_benchmark), 16,  8),
    ("overlap = 32（对照：冗余推理）", ...,                                8, 32),
]
```

实测结论（由代码在跑完后按真实数字生成，`app.py:2531-2549`）：

- **CPU 线程数 / `cudnn.benchmark` / `batch_size` 这几项差异 < 15%**（`app.py:2544` 的 `spread < 1.15` 分支）——瓶颈在 GPU 推理本身；
- **`overlap` 是最大的一项速度变量**：8 → 32 约慢 4 倍（`app.py:2540-2542` 会打印实测倍率）。

项目**不写没有实测支撑的结论**：结论文字完全由本次跑出的数字拼成（`app.py:2531` 注释「不做没测过的推断」）。

### 2.3 进度的真实性：hook 内部 tqdm

`audio-separator` 的 `mdxc_separator` 模块里用了 tqdm 循环分块推理（`app.py:174-177` 注释）：

```
for start_idx in tqdm(chunk_starts):   # RoFormer 分块推理
for batch in tqdm(batches):            # MDXC 分批推理
```

它**没有对外暴露进度回调**，所以只能猴补丁（monkey-patch）：`install_tqdm_hook()`（`app.py:191`）把该模块内的 `tqdm` 符号替换为一个子类 `_ProgressTqdm`：

```python
class _ProgressTqdm(_base_tqdm):
    def _vs_report(self):
        rep = _current_reporter()
        if rep is None:
            return
        rep.update_segment(self.n, self.total, token=id(self))

    def update(self, n=1):
        r = super().update(n)
        self._vs_report()
        return r

_mdxc.tqdm = _ProgressTqdm      # app.py:230
```

`self.n / self.total` 就是**真实的块计数**，因此进度条不是假的估算。

- reporter 存在 `threading.local()`（`app.py:179`），所以多任务/多线程互不串扰；
- hook 安装失败不会让程序挂掉，只记日志（`app.py:198-201`）。

### 2.4 进度分段的映射

`SeparationProgress`（`app.py:475`）负责把 `(n, total)` 映射到 0.06–0.94 的区间：

| 常量 | 值 | 含义 | 位置 |
| --- | --- | --- | --- |
| `P_START` | 0.02 | 入队/准备 | `app.py:467` |
| `P_LOAD_DONE` | 0.06 | 模型加载完成 | `app.py:468` |
| `P_SEP_SPAN` | 0.88 | 分离主体占比 | `app.py:469` |
| `P_SEP_MAX` | 0.94 | `0.06 + 0.88` | `app.py:470` |
| `P_DRE_LO` | 0.56 | 去回声模式的 1/2 阶段终点 | `app.py:471` |

```python
progress = min(P_SEP_MAX, P_LOAD_DONE + P_SEP_SPAN * frac)   # app.py:550
```

三条保证（`app.py:476-480` 的 docstring）：

1. 能拿到 tqdm → 按「第几个模型 `round_index` + 本轮完成比例」算；
2. 拿不到（如 Demucs / VR 架构）→ 回退为**按音频时长的经验估算**；
3. **进度单调不减，永不回退**。

经验估算的基数（`app.py:493-496`）：

```python
SECONDS_PER_AUDIO_SECOND = 0.30
self.est_total = max(20.0,
    self.duration * SECONDS_PER_AUDIO_SECOND * self.n_models * (self.overlap / 8.0))
```

即：模型数越多、overlap 越大，ETA 越长。

## 三、集成（Ensemble）融合算法

集成档位让多个模型各自跑一遍，再把**频谱**融合。可选算法共 9 个（`ENSEMBLE_ALGOS`，`app.py:607-617`）：

```python
ENSEMBLE_ALGOS = [
    "avg_fft", "min_fft", "max_fft",
    "avg_wave", "min_mag", "max_mag",
    "uvr_max_spec", "uvr_min_spec", "ensemble_wav",
]
```

这些字符串会被直接透传给 `audio-separator` 的 `ensemble_type` 参数，**融合数学由上游库实现**。下表说明各算法的语义与适用场景：

| 算法 | 在频谱上做什么 | 何时选 |
| --- | --- | --- |
| `avg_fft` | 多模型幅度谱**平均** | **默认**。最稳，谁的偏差都被摊薄；`builtin_vocal_revive` 用的就是它 |
| `min_fft` | 每个频点取**最小**幅度 | 保守、去残留最狠，但也最容易把真实内容一起削掉 |
| `max_fft` | 每个频点取**最大**幅度 | 保留最多细节，代价是各模型的伪影也会被留下 |
| `avg_wave` | 在**时域波形**上平均 | 不经过频谱域，听感更「自然」，但可能出现相位干涉 |
| `min_mag` | 幅度谱逐点取小 | 同 `min_fft` 的保守取向 |
| `max_mag` | 幅度谱逐点取大 | 同 `max_fft` 的激进取向 |
| `uvr_max_spec` | UVR 风格的**最大谱**策略 | 社区预设大量使用（`instrumental_clean` / `instrumental_full` 都是它） |
| `uvr_min_spec` | UVR 风格的**最小谱**策略 | 需要极致抑制串音时 |
| `ensemble_wav` | 波形域集成（库自带实现） | 想对比波形域效果时 |

> **已知限制 / 待确认**：以上是各算法**语义层面**的说明。`audio-separator 0.47.0` 内部对各算法的逐行实现细节（例如 `uvr_max_spec` 的具体加权方式）本仓库未做二次验证，需要精确行为请直接读上游 `audio_separator` 源码。

### 内置的三个集成预设

`catalog.json` 的 `presets` 段共 9 个社区预设，但 `app.py` 里另有 3 个**成员全部本地内置**的组合（内置于 `catalog.json` 的 `presets`，`builtin_*` 前缀）：

| 预设 Key | 成员 | 算法 | 定位 |
| --- | --- | --- | --- |
| `builtin_vocal_revive` | Revive V3e + BS-Roformer 1297 | `avg_fft` | **默认**，人声极致干净 |
| `builtin_vocal_dual` | BS-Roformer 1297 + 1296 | `avg_fft` | 人声双雄，稳定干净 |
| `builtin_vocal_triple` | 1297 + 1296 + InstVoc Duality V2 | `avg_fft` | 细节更饱满，更慢 |

其余 6 个社区预设（`vocal_full` / `instrumental_full` / `karaoke` 等，见 `catalog.json` 的 `presets`）**依赖未内置的权重**，离线模式下不会出现在下拉列表里；把权重放进 `models\` 后即可用。

## 四、离线设计

### 4.1 为什么要做离线守卫

`audio-separator` 默认会在模型缺失时**自动联网下载**。对一个宣称「音频不上传、模型全本地」的桌面工具来说，这是不可接受的：

- 用户可能在无网环境，程序会卡在下载超时上；
- 静默联网与「完全离线」的产品承诺矛盾。

### 4.2 实现方式

环境变量打底（`app.py:74`，以及 `start.bat:6-7`、`launcher.py:93-94`）：

```python
os.environ["HF_HUB_OFFLINE"] = "1"
os.environ["TRANSFORMERS_OFFLINE"] = "1"
```

再加一层**硬拦截**——`install_offline_guard()`（`app.py:157`）直接替换掉下载函数：

```python
def install_offline_guard():
    def _guard(self, url, path, *args, **kwargs):
        if os.path.exists(path):
            return
        raise RuntimeError(
            f"离线模式：本地缺少模型文件 {os.path.basename(str(path))}，已阻止联网下载。"
            "请先把该文件放入 models 目录。"
        )
    Separator.download_file_if_not_exists = _guard
```

要点：

- 文件**已存在就照常返回**，不影响正常流程；
- 缺失则 **raise**，而不是静默返回——错误会带着模型文件名冒到界面上，用户一眼知道缺哪个文件；
- 抛错发生在推理之前，所以是「快速失败」，不会让用户白等。

## 五、并发与任务模型

### 5.1 全局串行锁 `RUN_LOCK`

GPU 显存有限，多个分离任务同时推理会 OOM。因此全局只有一把锁（`app.py:1059`）：

```python
RUN_LOCK = threading.Lock()
```

`_wait_run_slot()` 在拿不到锁时把任务状态置为排队（`STATUS_QUEUED`，「排队中 · 前一个任务完成后自动开始」），拿到锁才开始加载模型。

也就是说：**允许多个任务同时提交并各自显示进度，但同一时刻只有一个在真正推理。**

### 5.2 后台线程 + JSON 台账

任务提交后立刻起后台线程（`submit_single` / `submit_batch`，`app.py:1481` / `1542`），主线程返回，UI 不阻塞。

任务状态落盘到 `tasks.json`（`TaskLedger`，`app.py:320`）：

- 每条任务记录状态、阶段、进度、时间戳、参数；
- `_live()`（`app.py:440`）在读取时动态补算 `elapsed`；
- `list_tasks()` 按 `created_at` 倒序（`app.py:454`）。

**这带来一个关键特性：刷新页面 / 切换标签都不会丢任务**，因为事实来源是磁盘上的台账，不是内存里的组件状态。

### 5.3 为什么只有一个 `gr.Timer`

早期实现给「单曲 / 批量 / 任务列表」各挂了一个 Timer，结果轮询失效。现在全局只挂**一个** Timer，且必须写在 `Blocks` 顶层并正常挂载（`app.py:4833-4834`）：

```python
# 全局轮询计时器：必须写在 Blocks 顶层并正常挂载（render=False 会让组件不上屏、tick 永不触发）
tick_timer = gr.Timer(2.0)
```

一个 tick 驱动三个页面的刷新（`poll_all`，`app.py:2311-2347`）。

### 5.4 轮询去重缓存与会话隔离

Gradio 每次回调都要序列化整个返回值，2 秒一次的全量轮询会把 CPU 吃满。解决办法是**按会话 + 按签名去重**：

- `_new_sid()`（`app.py:2207`）在 `demo.load` 时给每个页面（含每次刷新）发一个新会话 ID；
- `_sess(sid)` 取出该会话的去重桶；
- `_cached_upd(key, sig, value, sid)`（`app.py:2212`）：**签名没变就返回 `gr.update()` 空更新**，前端不重绘；
- `_cached_choices(key, sig, choices, sid)`（`app.py:2225`）：下拉选项同样去重。

会话隔离的原因（`app.py:4835-4836` 注释）：去重缓存按会话隔离，**保证新页面第一帧就能拿到真实内容**——否则新开的页面会命中旧页面的缓存而显示空白。

会话数量有上限 `_SESS_MAX`，超出时整体清空。

### 5.5 队列并发度

```python
demo.queue(default_concurrency_limit=4).launch(...)   # app.py:5178
```

默认并发 1 的话，长任务会把「暂停 / 继续 / 刷新」这些轻量事件堵在队列里；提到 4 之后轮询与控件保持响应。

### 5.6 暂停 / 继续

暂停不是「杀掉推理」，而是**门闸（gate）**：

- `_register_gate(tid)` / `_unregister_gate(tid)` 管理 `_GATES[tid] = threading.Event()`；
- 推理在块与块之间检查 `_pause_gate`，暂停时 `Event.wait()` 阻塞；
- `resume_task` 置位 Event 继续；
- `_is_paused(tid)` 先看内存 `_PAUSE_SET`，再看台账状态。

好处：暂停期间显存和模型保持加载，恢复后**不重跑已完成的块**。

### 5.7 下载后的自动清理

分离结果留在 `output\`，用户下载后就重复占空间了。做法：

- 页面上的下载链接绑定了 `fetch('/vs_del?f=' + path)`（`app.py:4491`）；
- 服务端路由 `@demo.app.post("/vs_del")` → `vs_mark_downloaded()`（`app.py:1966`）；
- 删除走 `_to_recycle_bin()`（`app.py:1872`），用 Windows 原生 `SHFileOperationW` **送进回收站**，不是硬删——误删可恢复。

页面上另有「清理本机副本」按钮（`cleanup_local_outputs`，`app.py:2027`）供手动清理。

## 六、去回声后处理数学

去回声是给 RVC 翻唱准备干净输入的可选链路（`run_dereverb()`，`app.py:1190`）。它的**收尾补偿**是这套方案里最容易踩坑的部分。

### 6.1 等响补偿（RMS 匹配）

```python
gain = min(max(_rms(ref[:n_ov]) / _rms(sig[:n_ov]), 0.2), 12.0)   # app.py:1167
```

- **只用「重叠区」算增益**：产物比原轨长/短时，用补零后的全长会把增益算偏（`app.py:1164`）；
- **上限放到 12 倍（约 +21.6dB）**：这类去回声/去混响模型实测可能把整轨压低**十几 dB**，早期 5 倍上限补不回来——这正是「去完之后音量跟原曲对不上」的直接原因（`app.py:1165-1166`）；
- 下限 0.2 是防止除极小值放大噪声。

### 6.2 频谱倾斜匹配（1/3 倍频程）

`_spectral_tilt_match(sig, ref, sr, max_db=6.0, f_lo=180.0, f_hi=16000.0)`（`app.py:1091`）把产物的**整体频谱倾斜**朝参考人声靠拢：

1. 加汉宁窗后取 `rfft`，算平均幅度谱（`app.py:1103-1105`）；
2. 以 `f_lo` 为起点、1/3 倍频程步进生成 40 个中心频率，截断到 `hi`（`app.py:1110-1111`）；
3. 每个频带算 `20*log10(mean(ref)/mean(sig))`，**限幅 ±max_db**（`app.py:1118-1119`）；
4. 用对数频率插值铺回全频段，再乘上低频 `ramp` 与高频 `fade` 边缘包络（`app.py:1120-1124`）；
5. 幅度域乘回信号（`app.py:1127`）。

关键设计取舍（`app.py:1096-1097` 与 `app.py:1136-1137`）：

> **只做「宽频带倾斜」修正 —— 不做窄带 / 共振峰提升，因此不会把刚刚压下去的回声能量重新抬起来。**

这是刻意为之：如果做窄带/共振峰 EQ，被去回声模型压制掉的那部分能量（恰恰包含回声）会被重新提起来，等于白干。

> ⚠️ **文档与代码不一致**：`_dereverb_postprocess` 的 docstring 写「限幅 ±4dB」（`app.py:1137`），但函数签名 `_spectral_tilt_match` 的默认值是 `max_db=6.0`（`app.py:1091`），且 `app.py:1172` 调用时未覆盖该参数，**实际生效的是 ±6dB**。此处以代码为准。

### 6.3 高频补回（默认关闭）

```python
if restore_air and sosfiltfilt is not None:
    sos = butter(4, air_cut / (sr / 2.0), btype='lowpass', output='sos')
    out = sosfiltfilt(sos, out, axis=0) + (ref - sosfiltfilt(sos, ref, axis=0))
    air = True
```

`air_cut = 8000.0`（`app.py:1131` 默认参数）。做法是把原人声 8kHz **以上**的成分加回来。

**为什么默认关**：老式 anvuew 去混响会吃掉 8kHz 以上空气感，需要补；但**新的去回声模型（De-Reverb-Echo V2 / Fused）实测完全不掉高频**，再补就等于把「原人声里的回声高频」又灌回去——越补回声越多（`app.py:1138-1140`）。

### 6.4 去回声模型的选择依据

`DEREVERB_CHOICES`（`app.py:661-674`）里最关键的实测结论（`app.py:658-660`、`app.py:697-698`）：

| 模型族 | 性质 | 实测 |
| --- | --- | --- |
| `anvuew` 系列（SDR 19.17 / 18.81） | **只是去混响** | 对离散回声（延迟尾巴）**几乎无效**，真实湿人声上 SDR 仅 15.1 |
| `Sucial De-Reverb-Echo` 系列 | **治回声的** | 同一素材 SDR 24.3（标签内记 13.48），且不掉电平、不掉高频 |

**遍数**（`DEREVERB_PASSES`，`app.py:699-702`）：实测「2 遍」对回声的额外削减极小（`-8.48 → -8.52dB`）却让耗时翻倍，所以**默认锁定 1 遍**，2 遍只留作极端情况手试。

### 6.5 只对人声轨处理

`_pick_vocals()`（`app.py:994`）有个必须避开的坑（`app.py:997-1000` 注释）：

> `audio-separator` 的输出名是 `歌名_(主干)_模型名.wav`，而像 `bs_roformer_vocals_revive_v3e` 这种**模型名本身就带 `vocals`**，若整名匹配就会把「其他 / 伴奏」轨误判成人声。

所以只认**括号里的主干标签**，并显式排除伴奏类标签（`app.py:1002`）：

```python
bad = ("instrumental", "other", "karaoke", "accompaniment", "inst_", "instrument")
```

### 分层关系

```
   用户
    │ 双击
    ▼
launcher.py（VocalSeparator.exe）──探端口──▶ 已在跑？直接开窗
    │ 没在跑
```

### 原生窗口的下载问题

WebView2 **默认不处理下载**，Gradio 的下载链接在原生窗口里点了没反应（浏览器里正常）。因此 `JsApi.save_file`（`launcher.py:199`）把 `/gradio_api/file=<本地路径>` 里的本地路径解出来，**直接复制到用户的「下载」目录**——因为这些文件本来就在本机，走复制比走网络更稳（`launcher.py:183-185` 注释）。
